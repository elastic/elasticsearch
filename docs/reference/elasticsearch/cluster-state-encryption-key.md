# Cluster state encryption [cluster-state-encryption]

Some {{es}} features need to store sensitive values, such as credentials for {{esql}} data federation, in cluster state. With **cluster state encryption**, this data is protected both at rest and in transit between nodes, so that secrets are never persisted or replicated in plain text.

These feature-managed secrets differ from [secure settings](docs-content://deploy-manage/security/secure-settings.md) in the {{es}} keystore. Secure settings are provided by the operator and stored locally on each node. They are not designed for secrets that features create or update through cluster APIs and then store in cluster state.

{{es}} generates a single, cluster-wide encryption key automatically. Features that need to persist secrets never handle the key directly. They call an internal encryption service that encrypts and decrypts values on their behalf. The key itself is never exposed through any API.

The first feature to use cluster state encryption is [{{esql}} data federation](/reference/query-languages/esql/esql-data-federation.md), which encrypts the credentials used to connect to external data sources.

:::{note}
Cluster state encryption is distinct from [customer-managed encryption keys](docs-content://deploy-manage/security/encrypt-deployment-with-customer-managed-encryption-key.md). Customer-managed keys protect an {{ech}} deployment's files and snapshots at the infrastructure layer. Cluster state encryption protects feature-managed secrets before {{es}} stores or replicates them in cluster state. The two mechanisms are complementary.
:::

## How the cluster state encryption key works [cluster-state-encryption-key-lifecycle]

{{es}} generates the cluster state encryption key automatically and stores it in cluster state, where it's distributed to every node. It's excluded from cluster state REST responses and from snapshots.

Each node keeps a copy of the key in memory. To survive a restart, a node also persists a copy of the key to local disk, protected by a password so it isn't stored in plain text.

## Protect the cluster state encryption key with a password [cluster-state-encryption-key-password]

To let a node persist the key to disk, it needs a password configured as a [secure setting](docs-content://deploy-manage/security/secure-settings.md) in the {{es}} keystore:

`cluster.state.encryption.password.<id>`
:   A secure setting holding an encryption password, identified by `<id>`.

`cluster.state.encryption.active_password_id`
:   The `<id>` of the password currently used to protect newly written keys.

These settings are node-local. Configure a different password value on each node. Password IDs can be the same across nodes.

Every master-eligible and data node needs a password. These nodes write cluster state to disk, and a node that can't persist the key can't persist cluster state at all. Other nodes, such as dedicated coordinating nodes, don't need one:

* {{es}} creates the cluster state encryption key only once every master-eligible and data node has a password configured. Until then, the elected master logs a warning that names the nodes without one, reports them in its health report, and checks again periodically.
* Once the key exists, a node without a password can't join the cluster. It logs `this node cannot join the cluster: the cluster uses a cluster state encryption key and this node cannot persist it` and keeps retrying. Configure the password in its keystore and restart it, or reload its secure settings.
* {{es}} rejects a secure settings reload that would remove the password from a node while the cluster uses the key. It also rejects a reload that removes the password the node's on-disk copy of the key is wrapped with. The node keeps using its previous settings only until it restarts: the keystore file has already changed, so after a restart the node can't join the cluster until you configure the password again. When you rotate the password, keep the old one until the node has rewrapped its copy of the key with the new one.
* A password that's configured but can't be used, such as one shorter than 14 characters in FIPS mode, counts as missing.

:::{warning}
Add both settings to every node's keystore before you reload secure settings on any node, and before any new node joins. A node without the password can't save cluster state. Refer to [known issues](/release-notes/known-issues.md#elasticsearch-9.6.0-known-issues).
:::

**On {{ech}} and {{ece}}**, the control plane supplies this password automatically.

**On self-managed standalone Stack** deployments, this password is generated by the [automatic security setup](docs-content://deploy-manage/security/self-auto-setup.md) on a node's first start, and stored in the keystore as `cluster.state.encryption.password.autoconfigured`.

If the automatic security setup doesn't run, [configure the password on every node](#cluster-state-encryption-configure-password) yourself.

`cluster.state.encryption.required`
:   Whether a password is required before {{es}} will store secrets using the cluster state encryption key. Defaults to `true`.

    :::{warning}
    Setting this to `false` is not recommended. {{es}} falls back to storing secrets in plain text instead, and logs a warning.

    :::

### Configure the password on every node [cluster-state-encryption-configure-password]

1. On every node, add a password and set it as active. For example, to use the password ID `v1`:

   ```sh
   bin/elasticsearch-keystore add cluster.state.encryption.password.v1
   bin/elasticsearch-keystore add cluster.state.encryption.active_password_id
   ```

   Enter `v1` when prompted for `active_password_id`.

2. On every node, confirm that both settings are listed:

   ```sh
   bin/elasticsearch-keystore list
   ```

3. Reload secure settings on all nodes at once:

   ```console
   POST /_nodes/reload_secure_settings
   ```

   Check that every node is in the response and that each node's `secure_setting_names` includes both settings. Don't reload nodes one at a time. The elected master can briefly step down while the nodes reload.

4. Send the following request directly to each node:

   ```console
   GET /_health_report/cluster_state_encryption
   ```

   Each node should report a green status, with `active_password_id` and `metadata_password_id` set to `v1`.

### Recover a node that's missing the password [cluster-state-encryption-recover-missing-password]

A master-eligible node without the password rejects cluster state updates but doesn't log an error itself. Instead, the elected master or another master-eligible node logs an error that names the affected node and contains `cannot wrap PEK for disk`. A data-only node logs the error itself. If most master-eligible nodes are affected, the cluster has no elected master, and the `cluster_state_encryption` health indicator reports an `unknown` status on every node.

1. Find the nodes missing the password by running `bin/elasticsearch-keystore list` on each node, or by checking the logs for the node names in `cannot wrap PEK for disk` errors.
2. Add `cluster.state.encryption.password.<id>` and `cluster.state.encryption.active_password_id` to the keystore of each affected node. Any password works.
3. Reload secure settings:

   ```console
   POST /_nodes/reload_secure_settings
   ```

   A node that the elected master has removed from the cluster isn't included in the response. Send the following request directly to each such node:

   ```console
   POST /_nodes/_local/reload_secure_settings
   ```

4. Once most master-eligible nodes have the password, the cluster elects a master. Send `GET /_health_report/cluster_state_encryption` directly to each node and check that it reports a green status.

Don't reset the cluster state encryption key to recover. Adding the password to the affected nodes restores the cluster without losing data.

### Upgrade existing deployments [cluster-state-encryption-upgrades]

You don't need to configure an encryption password to upgrade an existing deployment. If no password is configured after the upgrade, the cluster remains healthy and reports that cluster state encryption is not configured. Because encryption is required by default, {{es}} rejects attempts to store feature-managed secrets with an HTTP `503` response until a password is configured.

* **Self-managed deployments:** Automatic security setup doesn't run again during an upgrade. Before a feature first stores a managed secret, [configure the password on every node](#cluster-state-encryption-configure-password). A restart isn't required.
* **{{eck}} deployments:** ECK doesn't provision the password automatically during an upgrade. Before a feature first stores a managed secret, configure `cluster.state.encryption.password.<id>` and `cluster.state.encryption.active_password_id` through [ECK secure settings](docs-content://deploy-manage/security/k8s-secure-settings.md), then call `POST /_nodes/reload_secure_settings`. A restart isn't required.
* **{{ech}} and {{ece}} deployments:** When an existing deployment is upgraded to 9.5 or later, the control plane provisions the password and reloads the secure settings automatically.

### Rotate the encryption password [cluster-state-encryption-password-rotation]

You can rotate each node's password independently without restarting {{es}}. The following procedure rotates the password on one node. Repeat it for any other nodes whose passwords you want to rotate. Keep a node's old password available until that node has rewrapped its on-disk copy of the cluster state encryption key with the new password.

A node rewraps its copy the next time it rewrites the global cluster metadata on its disk, for example after a cluster settings update, a master election, or a change to the key. Index and mapping changes don't cause this. A change to the elected master's active password ID, or the next automatic key rotation, always causes this on every node. If you rotate the passwords on several nodes, rotate the elected master last, so that its change rewraps the copies on the other nodes too.

1. Add the new password to the node's local {{es}} keystore. For example, to use the password ID `v2`:

   ```sh
   bin/elasticsearch-keystore add cluster.state.encryption.password.v2
   ```

2. On the same node, set `cluster.state.encryption.active_password_id` to `v2`:

   ```sh
   bin/elasticsearch-keystore add -f cluster.state.encryption.active_password_id
   ```

3. Reload the secure settings on that node:

   ```console
   POST /_nodes/<node_id>/reload_secure_settings
   ```

4. Send the following request directly to the node's HTTP endpoint:

   ```console
   GET /_health_report/cluster_state_encryption
   ```

   Before proceeding, verify that the node reports `active_password_id` and `key_on_disk_password_id` as `v2`. `key_on_disk_password_id` is the password the node's own copy of the key is wrapped with. It changes only once the node rewraps its copy, as described above. `metadata_password_id` is the elected master's active password ID, not this node's.

5. Remove the old password from the node's keystore, then reload the secure settings on that node again. {{es}} rejects this reload while the node's copy of the key is still wrapped with the old password.

## Automatic key rotation [cluster-state-encryption-key-rotation]

{{es}} rotates the cluster state encryption key (not the password in the keystore) automatically. You can control the schedule with:

`xpack.encryption.key_rotation.interval`
:   How often the key is rotated. Defaults to `30d`. Set to `0` to disable automatic rotation.

`xpack.encryption.key_rotation.check_interval`
:   How often {{es}} checks whether rotation is due. Defaults to `1h`, must be at least `1s`, and can't be greater than `key_rotation.interval`.

## Check cluster state encryption health [cluster-state-encryption-key-health]

The `cluster_state_encryption` health indicator reports on the status of the cluster state encryption:

* **Green**: encryption is either working normally, or hasn't been configured (which is expected on most self-managed clusters that haven't set a password).
* **Yellow**: a master-eligible or data node has no usable password once the key exists, so it can't persist the key to disk, the elected master is waiting for nodes without a password before it creates the key, or the elected master holds no key and nothing is encrypted yet.
* **Red**: the elected master holds no key and encrypted secrets are stored. They can't be decrypted until the key is back.

The health report is calculated by the node that receives the request. Only the elected master knows which nodes it's waiting for: send the request to the elected master to see them in `nodes_without_password`.

### If the elected master holds no key [cluster-state-encryption-master-without-key]

A node that can't decrypt the key on its disk, for example because it restarted without its password, still starts. If it's elected master, encryption is unavailable on every node until it has the key again. Every node keeps its copy of the key on disk in the meantime. To recover:

* Configure the password that the elected master's copy is wrapped with on the elected master, as `cluster.state.encryption.password.<id>` together with `cluster.state.encryption.active_password_id`, then reload its secure settings. The elected master then reads the key from its disk.
* If that password is lost, fail the master over to a master-eligible node that can read its copy. For example, exclude the elected master from the voting configuration with `POST /_cluster/voting_config_exclusions?node_names=<node_name>`, which makes another master-eligible node take over. The new master reads the key from its own copy. Once the key is restored, remove the exclusion with `DELETE /_cluster/voting_config_exclusions?wait_for_removal=false`, since the former master stays in the cluster.

As when the key is first created, the elected master restores the key only once every master-eligible and data node has a password configured. Until then, it logs a warning that names the nodes without one and reports them in `nodes_without_password`.

The elected master logs a warning that says why it can't read its copy. Don't reset the key while another node might still hold it: a reset permanently deletes all encrypted data. To check, send `GET /_health_report/cluster_state_encryption` directly to each node. A node that reports `key_on_disk: true` holds a copy of the key, and `can_read_key_on_disk: true` means it can decrypt that copy with its current passwords.

## Reset the cluster state encryption key [cluster-state-encryption-key-reset]

:::{warning}
Resetting the cluster state encryption key is **destructive and irreversible**. Any data that was encrypted with the previous key is permanently lost.
:::

As a last resort, if the encryption password is lost or corrupted on every node and can't be recovered, you can discard the current cluster state encryption key and everything encrypted with it. Nodes can join while the elected master holds no key, so the cluster forms and accepts this request even if no node can read the key:

```console
POST /_encryption/_reset?accept_data_loss=true
```

The `accept_data_loss=true` query parameter is required. {{es}} generates a new cluster state encryption key on the next write.
